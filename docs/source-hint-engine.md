
> **Source Hint Engine Specification**
>
> Version: 1.0
>
> Status: **Locked**

---

# Purpose

The Source Hint Engine estimates where a selected user interface element is implemented within a project.

Its purpose is to narrow the search space for AI coding agents.

It does not identify files with certainty.

It produces evidence-backed probabilities.

---

# Design Philosophy

The Source Hint Engine answers one question:

> **"Where is this UI most likely implemented?"**

Not:

> **"Where is this UI implemented?"**

Certainty requires direct evidence.

The engine should communicate uncertainty explicitly.

---

# Responsibilities

The Source Hint Engine is responsible for:

* generating source hints
* evaluating evidence
* calculating confidence
* ranking candidate files
* explaining reasoning

It is not responsible for:

* reading source code
* modifying files
* browser automation
* DOM collection
* project scanning

It consumes information generated by other systems.

---

# Inputs

The engine may consume:

* DOM structure
* element attributes
* CSS classes
* IDs
* accessibility roles
* browser URL
* active route
* framework metadata
* project structure
* workspace metadata

Inputs are observational.

No inference occurs during collection.

---

# Candidate Discovery

Candidate discovery identifies possible implementation files.

Examples:

* page components
* layout components
* reusable UI components
* route files
* framework entry points

Candidate discovery should favour precision over quantity.

---

# Evidence Sources

Evidence may include:

* route matching
* component naming conventions
* file names
* framework structure
* CSS module names
* runtime metadata
* build metadata
* source maps (future)

Every hint should identify the evidence that produced it.

---

# Framework Awareness

Framework adapters contribute additional evidence.

Examples:

```text id="fj39hp"
Next.js

↓

app/dashboard/page.tsx

React Router

↓

routes/dashboard.tsx

SvelteKit

↓

routes/dashboard/+page.svelte
```

Framework-specific logic should never leak into the core engine.

---

# Ranking Pipeline

```text id="0y1m5t"
Candidates

↓

Evidence Scoring

↓

Confidence Calculation

↓

Ranking

↓

Top Results
```

Only the highest-confidence candidates should be returned.

---

# Confidence Model

Confidence combines:

* direct evidence
* convention matches
* structural similarity
* route correlation
* naming consistency

Confidence should never exceed the available evidence.

---

# Confidence Levels

```text id="ek3a4x"
0.95–1.00

Almost Certain

0.80–0.94

Very Likely

0.60–0.79

Likely

0.30–0.59

Possible

0.00–0.29

Weak
```

Consumers should treat lower-confidence hints cautiously.

---

# Source Hint Model

Each hint contains:

```text id="31pk9h"
File Path

Confidence

Evidence

Discovery Method

Framework

Timestamp
```

Hints should be fully explainable.

---

# Ranking Rules

The engine should:

* prefer fewer high-quality hints
* avoid duplicate paths
* remove conflicting evidence
* preserve deterministic ordering

The same inputs should always produce the same ranking.

---

# Route Correlation

Route information provides strong evidence.

Examples:

```text id="j63qpd"
/dashboard

↓

app/dashboard/page.tsx

/settings/profile

↓

routes/settings/profile.tsx
```

Route correlation alone should never guarantee correctness.

---

# Component Correlation

The engine may correlate:

* class names
* component names
* file names
* exported symbols
* directory conventions

Correlation strengthens confidence but does not prove implementation.

---

# False Positives

The engine should minimise false positives by:

* requiring multiple evidence sources
* reducing confidence for conflicting evidence
* preferring observed facts over conventions
* avoiding speculative guesses

Returning no hint is preferable to returning a misleading one.

---

# Missing Evidence

If evidence is insufficient:

* lower confidence
* explain missing evidence
* avoid inventing candidates

Unknown is a valid result.

---

# Caching

Hints may be cached using:

* project identifier
* route
* framework
* capture identifier

Caches must invalidate when project structure changes.

---

# Performance Targets

Candidate discovery

```text id="jvto7u"
<50 ms
```

Ranking

```text id="aw0d8d"
<25 ms
```

Hint generation

```text id="sqmgxj"
<100 ms
```

The Source Hint Engine should never become the bottleneck in Context Packet generation.

---

# Future Evidence

Future releases may incorporate:

* source maps
* component metadata
* language server indexes
* build manifests
* framework compiler metadata

Additional evidence should improve confidence without changing public interfaces.

---

# Failure Policy

If the engine cannot produce reliable hints:

* return an empty result
* include diagnostics
* preserve packet generation

Failure to identify source files should never prevent Context Packet creation.

---

# Explainability

Every hint must answer:

* Why was this file selected?
* What evidence supports it?
* How confident is the engine?
* What assumptions were made?

Explainability is a first-class requirement.

# Source Hint Engine North Star

The Source Hint Engine exists to reduce the search space for AI coding agents.

It should provide reliable, evidence-backed guidance without overstating certainty, allowing downstream agents to navigate large codebases more efficiently while remaining grounded in observable facts.
