# Purpose

This glossary defines the canonical terminology used throughout the Viskod documentation.

Its purpose is to ensure consistent language across documentation, implementation, APIs and future platform evolution.

Each term has exactly one canonical meaning.

---

# Usage Rules

Documentation should:

* use the canonical term
* avoid unnecessary synonyms
* reference glossary definitions where ambiguity may exist
* introduce new terminology only through documented additions

Consistent terminology reduces ambiguity for developers, contributors and plugin authors.

---

# A

## Agent

An external AI coding system that consumes Context Packets and other platform outputs.

Examples include coding assistants, autonomous software agents and AI development tools.

Viskod is **not** an Agent.

---

## API

A stable public interface exposed by the platform.

Internal implementation details are not part of the API.

---

## Architecture

The collection of platform components, responsibilities and relationships that define how Viskod operates.

Architecture describes structure rather than implementation.

---

# B

## Browser Runtime

The subsystem responsible for interacting with supported browsers, capturing visual state and coordinating browser operations.

The Browser Runtime is one of the platform's primary evidence sources.

---

# C

## Capture

The process of collecting visual or contextual evidence from supported environments.

Captures are deterministic and reproducible.

---

## Capture History

A chronological record of completed captures maintained by Studio.

Each entry includes a capture ID, timestamp, page, selection, and packet version.

Capture History entries are immutable.

---

## Capture Pipeline

The subsystem responsible for persisting, managing and exporting captured evidence.

Responsibilities include screenshot storage, capture metadata, retention policies, cleanup and export.

The Capture Pipeline never analyses data or interacts with the browser directly.

---

## Capability

A granular permission granted to plugins or public APIs.

Capabilities explicitly define what an extension may perform.

NOTE: The general concept of "a platform capability" (e.g., screenshot capture) is distinct from "a Capability" in the permission sense. Permission-mode Capabilities are always explicitly declared and revocable.

---

## CLI

The official command-line interface for interacting with Viskod.

The CLI exposes platform capabilities as deterministic, scriptable commands suitable for developers, CI/CD pipelines and automation workflows.

---

## Context

Structured information describing a project, interface or execution environment.

Context is evidence-driven rather than inferred.

---

## Context Explorer

A user interface for browsing Context Packets and related artefacts.

---

## Context Packet

The primary structured output generated by the Visual Context Engine.

A Context Packet contains deterministic information that external systems may consume.

---

# D

## Diagnostics

Structured information describing platform health, execution state or failures.

Diagnostics support debugging and observability.

---

# E

## Event

A structured notification emitted by the platform describing a meaningful occurrence.

Events follow documented schemas.

---

## Event Bus

The platform's integration boundary for asynchronous, publish-subscribe communication between subsystems.

The Event Bus transports immutable events from publishers to subscribers. It owns no business logic, makes no decisions, and never initiates actions.

Publishers (e.g., Browser Runtime) emit events without knowing which subscribers consume them. Subscribers (e.g., Visual Context Engine) register interest in specific event types.

The Event Bus does not replace command-style service invocation (see **VCE → Browser Runtime** in [Architecture](./architecture.md)).

---

## Evidence

Verified information collected directly from supported sources.

Evidence always takes precedence over assumptions.

---

## Extension

A capability added to the platform through the Plugin System.

Extensions interact through stable public contracts.

---

# F

## Framework Adapter

A platform component that understands the conventions of a supported application framework.

Adapters provide framework-specific knowledge without changing platform architecture.

---

# I

## Invariant

A guarantee that must remain true regardless of implementation details or future evolution.

Invariants form the foundation of architectural stability.

---

# M

## MCP

Model Context Protocol.

The primary protocol used for structured communication between Viskod and external AI systems.

---

## Manifest

The metadata describing a plugin, including identity, version, permissions and capabilities.

---

# O

## Overlay

A visual annotation rendered on top of captured browser content by the Overlay System.

Overlays enhance understanding without modifying the underlying application.

---

# P

## Overlay System

The architectural subsystem responsible for rendering visual annotations on captured browser content.

The Overlay System injects visual indicators (highlights, labels, measurement overlays) into the inspected page without modifying the application's behaviour, layout or style.

The Browser Runtime's Overlay Manager implements the Overlay System at runtime.

---

## Packet

See **Context Packet**.

---

## Permission

An authorisation granted to a user, plugin or subsystem.

Permissions determine which actions may be performed.

---

## Platform

The complete Viskod system (Visual Context Platform), including all documented subsystems and public interfaces.

In architectural documentation, "the Platform" refers to the entire system architecture, not any single subsystem.

---

## Plugin

An extension that integrates with Viskod using the public Plugin API.

Plugins must not depend on internal implementation details.

---

## Plugin API

The stable public interface through which plugins interact with the platform.

---

## Project Scanner

The subsystem responsible for analysing repositories and collecting project metadata.

---

# R

## Repository

The authoritative source of project code and related assets.

The repository is one of the platform's primary sources of truth.

---

## Resource

A platform-managed entity exposed through public APIs.

Resources may include Context Packets, captures, diagnostics or configuration objects.

---

# S

## Runtime Resource

A managed computational resource allocated and tracked by the platform.

Examples include browser sessions, memory, storage, cache, network connections, worker threads, plugin instances and file handles.

Every runtime resource has a defined owner and lifecycle.

---

## SDK

The official software development kit for integrating with Viskod.

---

## Selection

A user-defined region, element or scope identified for further analysis.

---

## Selection Engine

The subsystem responsible for processing and managing user selections.

---

## Selection Engine

The subsystem responsible for converting user pointer interactions into structured selection targets.

The Selection Engine validates DOM node candidates, manages selection state, and coordinates with Browser Runtime and Studio through the Event Bus.

---

## Source Hint

Structured metadata indicating where relevant information is likely to exist.

Hints assist navigation without replacing evidence.

---

## Source Hint Engine

The subsystem responsible for generating and managing Source Hints.

---

## Studio

The primary graphical interface of the Viskod platform.

Studio coordinates workflows while remaining independent of core platform services.

---

# T

## Tool

A documented public capability exposed by the platform.

Tools should remain deterministic and versioned.

---

# V

## Version

A semantic identifier representing a released platform state.

Versions follow Semantic Versioning.

---

## Viskod

The Visual Context Platform. See **Platform**.

Viskod is the proper name of the platform product. In architectural documentation, "the Platform" refers to the complete system; "Viskod" may be used interchangeably when the product identity is relevant.

---

## Visual Context

Structured visual evidence describing the current state of an application or interface.

Visual Context is collected rather than generated.

---

## Visual Context Engine

The core subsystem responsible for transforming evidence into structured Context Packets.

It is the central processing component of the platform.

---

# W

## Workspace

A logical environment containing projects, settings and related platform resources.

Workspaces organise development activities without altering repository structure.

---

# Canonical Principles

The following statements define the platform's terminology:

* The browser is the source of truth.
* The repository is the source of truth.
* Evidence precedes inference.
* Context is deterministic.
* Plugins extend the platform.
* Public APIs define platform boundaries.
* Architecture is implementation-independent.
* Documentation is part of the product.

---

# Naming Conventions

Documentation should use the following forms consistently:

| Preferred               | Avoid                                                |
| ----------------------- | ---------------------------------------------------- |
| Visual Context Platform | Visual IDE                                           |
| Viskod                  | App / Tool / Utility                                 |
| Visual Context Engine   | AI Engine                                            |
| Context Packet          | Prompt                                               |
| Browser Runtime         | Browser Connector                                    |
| Capture Pipeline        | Capture Manager, `capture-manager/`                  |
| Project Scanner         | Code Scanner                                         |
| Source Hint             | Suggestion                                           |
| Source Hint Engine      | Code Locator                                         |
| Selection Engine        | Element Picker                                       |
| Overlay System          | Annotation Layer, Info Bar                           |
| Plugin API              | Extension Interface                                  |
| Studio                  | Dashboard (unless referring to a specific UI screen) |
| Workspace               | Session (unless technically accurate)                |
| Repository              | Project Folder                                       |
| Diagnostics             | Error Reporter                                       |
| Runtime Resource        | System Resource (generic)                            |

The glossary guarantees:

* consistent terminology across documentation
* stable architectural language
* implementation-independent definitions
* backwards-compatible terminology where practical

# Glossary North Star

The Viskod Glossary exists to provide a single, authoritative vocabulary for the Visual Context Platform.

Its responsibility is to eliminate ambiguity, preserve architectural consistency and ensure that every contributor, plugin author and user interprets the platform's terminology in exactly the same way.
