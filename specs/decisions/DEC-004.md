# DEC-004: Event Bus Transport Strategy

**Date:** 2026-07-28
**Status:** Accepted
**Author:** Architecture
**Related Specification:** SPEC-007 (event-bus)

## Context

SPEC-007 (event-bus) mandates an Event Bus as the integration boundary between subsystems but leaves the transport mechanism open. The decision is whether event delivery is in-process (same Node.js event loop), inter-process (IPC), or a hybrid.

## Decision

**Option A: In-process EventEmitter.**

All subscribers run in the same Node.js process as the publisher. The EventBus is backed by a lightweight wrapper around Node.js's built-in `EventEmitter`. The public interface — `publish(topic, payload)`, `subscribe(topic, handler)`, `unsubscribe(topic, handler)` — is transport-agnostic and exposes no in-process implementation details.

## Alternatives Considered

- **Option B (IPC via named pipes / Unix sockets):** Process isolation improves fault tolerance — a crashing subscriber does not take down the publisher. However, every message incurs serialisation overhead and at least one kernel round-trip. For Phase 1, where all subsystems run in a single desktop host process, this cost is pure overhead with no compensating benefit. IPC also introduces connection lifecycle management, reconnection logic, and serialisation error handling that add surface area for bugs.
- **Option C (Hybrid — in-process for same process, IPC bridge for cross-process):** Maximum flexibility but doubles the implementation and test surface. Phase 1 has no cross-process subscribers. Building a hybrid transport before cross-process use cases exist violates the engineering principle of avoiding premature optimisation.

## Consequences

- Zero serialisation overhead — events are passed by reference within the same event loop.
- Simplified debugging: a single stack trace spans publisher and subscriber.
- No connection lifecycle, reconnection, or serialisation error handling required in Phase 1.
- The EventBus interface (`publish`, `subscribe`, `unsubscribe`) is defined as a TypeScript interface. If process separation is needed in Phase 2, a new IPC-backed implementation of this interface can be swapped in without changing any subscriber code. The **interface is the transport boundary** — the in-process implementation is an implementation detail.
- All subscribers must be loaded in the same process; a misbehaving subscriber can block the event loop. Mitigation: subscriber handlers are expected to be non-blocking. Zalgo prevention is enforced by the EventBus contract (handlers must not synchronously throw or hang).
