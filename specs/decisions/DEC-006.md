# DEC-006: P0 Context Packet Persistence Format

**Date:** 2026-07-28
**Status:** Accepted
**Author:** Architecture
**Related Specification:** SPEC-009 (VCE)

## Context

SPEC-009 (Visual Context Engine) needs a persistence format for Context Packets in Phase 0. The Capture Pipeline (SPEC-010) is a Phase 1 concern and is not yet implemented. P0 needs a storage strategy that is simple, debuggable, requires no additional dependencies, and supports the immutability guarantee defined by SPEC-009 (packets are never modified after creation).

## Decision

**Option A: JSON file per packet.**

Each Context Packet is written as a single JSON file to `.viskod/context/{packetId}.json`. The packet ID is a UUIDv7 (time-ordered). Files are written atomically (write to temp file, then rename) to prevent partial reads. Packets are append-only — once written, the file is never modified. Reading lists all `.json` files in the directory, sorted by filename (UUIDv7 sort order equals creation order).

## Alternatives Considered

- **Option B (SQLite database):** Enables structured queries (find packets by URL, by timestamp range, by element selector) and is more efficient for large datasets. However, SQLite requires the `better-sqlite3` native addon or `node:sqlite` (Node.js 22 experimental). Either adds a build dependency or an experimental-API dependency. Phase 1 packet volumes are expected to be small (tens to hundreds of packets per session), making query performance irrelevant. SQLite can be adopted transparently in Phase 2 behind the same storage interface if query patterns demand it.
- **Option C (Binary format — MessagePack):** Compact and fast to encode, but not human-readable. Debugging a Context Packet stored as binary requires a decoder tool. JSON files can be inspected with any text editor or `cat`. The space savings are negligible at Phase 1 data volumes (a typical Context Packet is 2–20 KB).

## Consequences

- Zero additional dependencies. File I/O uses only `fs.promises` from the Node.js standard library.
- Each packet is a standalone file — trivially inspectable, deletable, and exportable.
- File-per-packet naturally enforces the immutability guarantee: there is no database UPDATE statement to misuse; files are written once and never overwritten.
- Storage grows linearly with captured packets. No automatic retention or eviction in P0 — the Capture Pipeline (P1) will introduce retention policies, deduplication, and export functionality.
- UUIDv7 primary keys provide time-ordered sort without a separate timestamp index.
- No schema migration problem — the packet Zod schema is the schema. If the schema changes between versions, old files fail validation and are skipped or migrated by a one-time script.
- Directory listing performance degrades with very large packet counts (10,000+). This is a known limitation accepted for P0. The Capture Pipeline (P1) will introduce sharding or a database backend if needed.
