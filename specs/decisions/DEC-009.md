# DEC-009: Selection Engine ↔ Overlay System Communication

> **Decision ID:** DEC-009
> **Date:** 2026-07-28
> **Status:** Approved
> **Affected Specifications:** SPEC-014 (selection-engine), SPEC-022 (overlay-system), SPEC-008 (browser-runtime)

---

## Context

The P0 vertical slice had the overlay script (injected by Browser Runtime) handling both pointer event capture AND element resolution directly. This conflates two concerns:

1. **What element is selected** — belongs to Selection Engine (SPEC-014)
2. **How the selection is displayed** — belongs to Overlay System (SPEC-022), rendered by Browser Runtime's Overlay Manager

The architecture baseline (`docs/architecture.md` §Selection Engine, §Overlay System) defines these as separate subsystems that communicate through the Event Bus. The P0 stub merged them because Selection Engine didn't exist yet.

Phase 2 introduces Selection Engine as a separate package. The question is: how should the overlay script communicate pointer events to the Selection Engine?

---

## Options Considered

### Option A: Overlay script calls Selection Engine directly

The overlay script would import Selection Engine logic and resolve elements itself.

**Rejected because:**
- The overlay runs in the browser page context (sandboxed by Shadow DOM)
- Selection Engine runs in the main Node.js process
- Direct cross-process communication from page to main process would require a custom protocol
- Violates architecture boundary: Selection Engine should own resolution, not the overlay

### Option B: Browser Runtime intercepts overlay events and calls Selection Engine

`postMessage` from overlay → Browser Runtime listener → BR calls Selection Engine directly.

**Rejected because:**
- Browser Runtime should never import or call Selection Engine directly (architecture boundary)
- BR's responsibility ends at observation and control; selection resolution is above BR's layer
- Creates a back-channel that bypasses Event Bus

### Option C: Event Bus-based communication (Selected)

```
Overlay (in-page) → postMessage → Browser Runtime → EventBus.publish(InteractionEvent)
  → Selection Engine subscribes to InteractionEvent
  → Selection Engine resolves target, validates, produces SelectionSnapshot
  → Selection Engine publishes HighlightRequested
  → Browser Runtime subscribes to HighlightRequested
  → Browser Runtime calls overlay:highlight (postMessage back to page)
```

All communication flows through the Event Bus, preserving the architecture's unidirectional dependency rules.

---

## Decision

**The Selection Engine and Overlay System communicate exclusively through the Event Bus.** The Browser Runtime acts as a protocol bridge between the in-page overlay (postMessage) and the Event Bus (events), but performs no selection logic.

### Event Flow

```
1. User moves mouse over element in browser
   → Overlay script captures pointermove
   → Overlay sends: postMessage({ source: '__viskod_overlay', type: 'overlay:element-hovered', data: { selector, boundingBox, tagName } })

2. Browser Runtime receives postMessage
   → BR validates data (not analysis — just structural validation)
   → BR publishes: EventBus.publish(InteractionEvent { type: 'element-hovered', selector, boundingBox, tagName })

3. Selection Engine subscribes to InteractionEvent(type='element-hovered')
   → SE resolves target from selector + boundingBox
   → SE evaluates visibility
   → SE publishes: EventBus.publish(HighlightRequested { selector, boundingBox, mode: 'hover' })

4. Browser Runtime subscribes to HighlightRequested
   → BR calls overlay script: postMessage({ command: 'overlay:highlight', selector, mode: 'hover' })
   → Overlay script renders hover highlight
```

### Click → Selection Flow

```
5. User clicks element
   → Overlay sends: postMessage({ type: 'overlay:element-clicked', data: { ... } })
   → BR publishes: InteractionEvent { type: 'element-clicked', ... }

6. Selection Engine subscribes
   → SE validates element (DOM attachment, context, frame)
   → SE constructs hierarchy
   → SE collects accessibility metadata
   → SE records geometry
   → SE produces SelectionSnapshot
   → SE publishes: EventBus.publish(SelectionChanged { snapshot })
   → SE publishes: EventBus.publish(HighlightRequested { selector, mode: 'selection' })

7. VCE subscribes to SelectionChanged
   → VCE generates Context Packet with validated selection
```

### Responsibility Boundaries

| Component | Owns | Does NOT Own |
|-----------|------|-------------|
| Overlay System | CSS, Shadow DOM, highlight rendering, pointer event capture, postMessage protocol | Element resolution, validation, selection state |
| Browser Runtime | postMessage ↔ Event Bus bridge, overlay injection/removal | Selection logic, element hierarchy |
| Selection Engine | Target resolution, validation, hierarchy, visibility, accessibility, selection state, SelectionSnapshot | Rendering, DOM injection, CSS |
| Event Bus | Message transport, subscription delivery | Business logic, message interpretation |

## New Event Types

### InteractionEvent (published by Browser Runtime)

```typescript
interface InteractionEvent {
  eventId: string;
  eventType: 'BR_EVENT:ELEMENT_HOVERED' | 'BR_EVENT:ELEMENT_CLICKED';
  timestamp: string;
  version: '1.0.0';
  source: 'browser-runtime';
  correlationId: string;
  payload: {
    selector: string;
    boundingBox: BoundingBox;
    tagName: string;
    pointerX?: number;
    pointerY?: number;
  };
}
```

### HighlightRequested (published by Selection Engine)

```typescript
interface HighlightRequestedEvent {
  eventId: string;
  eventType: 'SE_EVENT:HIGHLIGHT_REQUESTED';
  timestamp: string;
  version: '1.0.0';
  source: 'selection-engine';
  correlationId: string;
  payload: {
    selector: string;
    boundingBox: BoundingBox;
    mode: 'hover' | 'selection' | 'diagnostics' | 'clear';
    label?: string;
    labelPosition?: { x: number; y: number };
  };
}
```

## Consequences

### Positive
- Clean separation: Overlay System renders; Selection Engine decides
- Architecture boundaries preserved (no BR → SE direct calls)
- All communication auditable through Event Bus (with history enabled)
- Each subsystem is independently testable (mock events)
- Future: Selection Engine can receive selections from Studio or MCP without overlay involvement

### Negative
- Additional Event Bus traffic for every pointermove event
- Latency: postMessage → EventBus → resolve → EventBus → postMessage round-trip

### Mitigations
- InteractionEvent for hover is debounced (50ms) at the overlay script level
- Selection Engine processing is <50ms total (within budget)
- Event Bus history is configurable (can be disabled for hover events to reduce memory)
- The overlay script already limits hover events to when mode is 'hover' or 'selection'

---

## Implementation Impact

### Browser Runtime Changes
- `injectOverlay()` must register a `postMessage` listener that publishes to Event Bus
- Subscribe to `SE_EVENT:HIGHLIGHT_REQUESTED` and forward to overlay via `postMessage`
- No selection logic added; purely a bridge

### Selection Engine Changes
- Subscribe to `BR_EVENT:ELEMENT_HOVERED` and `BR_EVENT:ELEMENT_CLICKED`
- Implement `resolveTarget()` from interaction events
- Publish `SE_EVENT:HIGHLIGHT_REQUESTED` after resolution

### Overlay System Changes
- No changes needed; overlay already sends `postMessage` for hover and click events
- Overlay already responds to `overlay:highlight` commands received via `postMessage`
