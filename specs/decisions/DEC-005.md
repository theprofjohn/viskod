# DEC-005: Overlay Injection Strategy

**Date:** 2026-07-28
**Status:** Accepted
**Author:** Architecture
**Related Specification:** SPEC-008 (browser-runtime)

## Context

SPEC-008 (browser-runtime) needs a strategy for injecting the selection overlay into the inspected page. The overlay provides visual feedback for element selection: highlighting, bounding boxes, labels. The injection method affects when the overlay activates, whether it interferes with application bootstrapping, and how tightly it couples to the underlying browser engine.

## Decision

**Option B: Playwright `addScriptTag` after page load.**

The overlay script is injected via `page.addScriptTag({ content, type: "module" })` after the page's `load` event has fired. The overlay script attaches a Shadow DOM root to a dedicated container element, isolating overlay styles and DOM from the application. All overlay logic — selection handling, highlight rendering, label display — is self-contained in this injected module.

## Alternatives Considered

- **Option A (Playwright `addInitScript`):** Injects the overlay script before any page scripts execute. This guarantees the overlay is present during the application's entire lifecycle but risks interfering with application bootstrapping — the injected script runs in the page's JavaScript context before the application's own `DOMContentLoaded` handlers, potentially affecting timing-sensitive initialisation. The application is not Viskod's property; Viskod must inspect without perturbing. Running code before the application is a perturbation.
- **Option C (Chrome DevTools Protocol directly):** Bypasses Playwright entirely, sending overlay commands over CDP. This provides the lowest-level control but creates a hard coupling to Chromium internals. The architecture principle states that Browser Runtime owns browser interaction **through Playwright only**. CDP direct usage fractures the abstraction, blocks future multi-browser support, and introduces a second browser-control surface that must be tested and maintained.

## Consequences

- Overlay styles and DOM are isolated in Shadow DOM. Application CSS cannot leak into the overlay, and overlay styles cannot corrupt the application.
- The overlay activates deterministically after `load`, so the application has fully rendered before Viskod attaches. Users will not see the overlay during initial paint, which is the intended behaviour.
- All browser interaction remains within Playwright's public API. Chromium-specific internals are never referenced directly.
- If the application uses a SPA router that replaces the DOM after initial load, the overlay container may be removed. Mitigation: a `MutationObserver` in the overlay script detects removal and reattaches.
- Cross-origin iframes embedded in the inspected page are not overlayed — Playwright's `addScriptTag` operates in the main frame only. This is acceptable for Phase 1; cross-origin iframe overlays can be addressed in a future specification.
